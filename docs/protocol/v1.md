# Asterism Node ↔ Control Plane protocol, version 1

Normative specification. The executable form is `src/protocol.rs`; where the two
disagree, that is a bug in one of them.

## 0. Direction and scope

The Node **dials out**. It never listens for the Control Plane, and adding an
inbound listener to the Node is out of scope for every version of this protocol.

```
Asterism Node  ──── outbound HTTPS (enrollment) ────▶  Control Plane
Asterism Node  ──── outbound WSS  (session)     ────▶  Control Plane
```

Two endpoints, both derived from one configured base URL:

| Purpose | Path | Transport |
| --- | --- | --- |
| Enrollment | `POST /v1/node/enroll` | HTTPS |
| Session | `GET /v1/node/session` | WSS |

## 1. Transport security

* `https://` and `wss://` are mandatory. Server certificates are verified
  against the platform trust store; verification cannot be disabled.
* `http://` and `ws://` are accepted **only** when both hold:
  1. the host is loopback (`127.0.0.0/8`, `::1`, `localhost`), and
  2. `development.allow_plaintext_loopback` is explicitly set.
* Plaintext to a non-loopback host is refused even with the flag set.

## 2. Enrollment

One-time, and the token is never stored.

**Request**

```http
POST /v1/node/enroll
Authorization: Bearer <one-time-enrollment-token>
Content-Type: application/json

{
  "public_key": "<base64 Ed25519 public key, 32 bytes>",
  "public_key_fingerprint": "<lowercase hex SHA-256 of the public key>",
  "display_name": "build-host-1",
  "supported_protocol_versions": [1],
  "software_version": "0.1.0"
}
```

**Response `200`**

```json
{
  "node_id": "node-1",
  "protocol_version": 1,
  "server_metadata": {}
}
```

Rules:

* the token is consumed on first successful use; a second attempt returns `401`;
* the Control Plane stores the public key against the assigned `node_id`;
* the Node persists `node_id` and the endpoint, and **discards the token**;
* a Node that already holds a `node_id` refuses to enroll again. Re-enrollment
  requires an explicit reset workflow, which v1 does not define.

## 2.1 Canonical JSON

Wherever this specification says a value is **digested**, it is first encoded as
**canonical JSON**:

* object keys sorted lexicographically by their UTF-16 code units, **recursively**;
* no insignificant whitespace;
* strings emitted as UTF-8, with only the escapes JSON requires;
* integers emitted without exponent, sign only when negative;
* `null` emitted literally.

The digest is SHA-256 over those UTF-8 bytes, rendered lowercase hex.

> **Defect record (Phase G).** The first draft said only "SHA-256 of a JSON
> value". Two independent implementations disagreed as a result: Rust's
> `serde_json` orders map keys while JavaScript's `JSON.stringify` preserves
> insertion order, so `{"b":2,"a":1}` digested differently in each. The rule
> above resolves it. It is a clarification, not a wire change: the Rust Node
> already produced sorted output, so no deployed behaviour changed and protocol
> v1 remains compatible. Fixture `digest_vectors.key_order` pins it.

## 3. Envelope

Every WebSocket frame is one JSON object:

```json
{
  "protocol_version": 1,
  "message_id": "1b4e28ba-2fa1-11d2-883f-0016d3cca427",
  "type": "server.command",
  "timestamp": 1786475448672,
  "correlation_id": "optional-message-id",
  "payload": {}
}
```

| Field | Rule |
| --- | --- |
| `protocol_version` | Must be supported by the receiver, else `unsupported_version` |
| `message_id` | UUID v4, 1..=128 chars, unique per message |
| `type` | 1..=64 chars; unknown types get `unknown_message_type` |
| `timestamp` | Wall-clock ms, **informational only** — never a replay defence |
| `correlation_id` | The `message_id` this frame answers |
| `payload` | Type-specific object |

Limits: frames are capped at **1 MiB**, command payloads at **128 KiB**.
Oversized frames are rejected, never buffered. Unknown *optional* fields are
tolerated for forward compatibility; malformed frames produce a typed error and
never terminate the session.

## 4. Version negotiation

`client.hello` carries `supported_versions`. The Control Plane intersects it
with its own set and selects the **highest shared** version, returning it in
`server.challenge`. No shared version means the session is closed with
`unsupported_version`.

## 5. Handshake

```
Node                                Control Plane
 │── client.hello ───────────────────────▶│
 │◀───────────────────── server.challenge │
 │── client.authenticate ────────────────▶│
 │◀───────────────────────── server.ready │
```

**`client.hello`**

```json
{
  "supported_versions": [1],
  "node_id": "node-1",
  "instance_id": "node_6ce3beb2f38367ce",
  "public_key_fingerprint": "165db83b...",
  "client_nonce": "<base64, 32 random bytes>",
  "capabilities_digest": "<sha256 hex of the capabilities document>",
  "software_version": "0.1.0"
}
```

**`server.challenge`**

```json
{
  "protocol_version": 1,
  "session_id": "sess-906c829d-...",
  "server_nonce": "<base64, 32 random bytes>",
  "issued_at": 1786475448000,
  "expires_at": 1786475478000
}
```

**`client.authenticate`**

```json
{"session_id": "sess-906c829d-...", "signature": "<base64 Ed25519 signature>"}
```

**`server.ready`**

```json
{"session_id": "sess-906c829d-...", "protocol_version": 1, "server_metadata": {}}
```

### 5.1 Canonical signing transcript

The Node signs the **exact bytes** of a JSON object with **sorted keys** and no
insignificant whitespace, built from a string-valued map. Every value is a
string, so the encoding cannot depend on numeric formatting.

Fields, in canonical (sorted) order:

```
capabilities_digest, client_nonce, domain, expires_at, instance_id,
issued_at, node_id, protocol_version, server_nonce, session_id
```

`domain` is the constant `asterism-node-auth/v1`. Its presence is what stops a
signature produced here from being valid for any other purpose.

The transcript is itself canonical JSON as defined in §2.1, with the additional
rule that **every value is a string** — including `protocol_version`,
`issued_at`, and `expires_at` — so the encoding cannot depend on how a language
renders numbers.

Example of the exact signed bytes:

```json
{"capabilities_digest":"9f8c...","client_nonce":"Yb2...","domain":"asterism-node-auth/v1","expires_at":"1786475478000","instance_id":"node_6ce3beb2f38367ce","issued_at":"1786475448000","node_id":"node-1","protocol_version":"1","server_nonce":"Kd1...","session_id":"sess-906c829d-..."}
```

Both sides build these bytes independently and must agree byte-for-byte. The
signature is Ed25519 over them, verified against the public key registered at
enrollment. Verification uses the crypto library's own constant-time comparison;
no signature bytes are compared by hand, and no bespoke hash is defined anywhere
in this protocol — SHA-256 is used wherever a digest is needed.

### 5.2 Authentication rules

The Control Plane MUST refuse the session when:

* the challenge has expired (`challenge_expired`);
* the `server_nonce` was already used (`challenge_replayed`);
* the `node_id` is unknown (`unknown_node`);
* the signature does not verify (`authentication_failed`);
* the `node_id` does not match the key that signed.

Replay protection rests on the **nonces**, not on `timestamp`.

## 6. Liveness

`client.heartbeat` → `server.heartbeat.ack`, in addition to WebSocket
ping/pong. Heartbeat payloads carry only safe summaries:

```json
{
  "instance_id": "node_6ce3beb2f38367ce",
  "connection_state": "connected",
  "registered_projects": 1,
  "active_runs": 0,
  "draining": false,
  "software_version": "0.1.0"
}
```

Never included: host paths, environment variables, credentials, prompt content,
source code, or raw event payloads.

Timeout decisions use a **monotonic** clock; wall-clock values are for reporting
only. Missing `heartbeat.missed_limit` consecutive intervals with no traffic
drops the session and triggers reconnect.

## 7. Commands

Control Plane → Node:

```json
{
  "type": "server.command",
  "payload": {
    "command_id": "cmd-1",
    "command": "runs.create",
    "project_id": "phase-a",
    "payload": {"input": "..."}
  }
}
```

Node → Control Plane, in order:

1. `client.command.accepted` — `{"command_id": "cmd-1"}`, correlated to the
   command's `message_id`. Sent only after the command is durably recorded.
2. `client.command.result`:

```json
{
  "command_id": "cmd-1",
  "state": "completed",
  "result": {},
  "error_code": null,
  "error_message": null,
  "deduplicated": false
}
```

3. `server.command.result.ack` — `{"command_id": "cmd-1"}`, which releases the
   result from the Node's outbox.

### 7.1 Allowed commands

Exactly this set; anything else is `forbidden_command`:

`capabilities.get`, `projects.list`, `runs.create`, `runs.list`, `runs.get`,
`runs.cancel`, `runs.retry`, `approvals.resolve`, `events.subscribe`,
`events.unsubscribe`, `node.drain`.

Explicitly **not** available to the Control Plane: arbitrary shell, arbitrary
host paths, HTTP proxying, provider authentication, project credential access,
Node identity export, Docker commands, project removal, and enabling the unsafe
native Codex runtime.

Every command is executed through the same `NodeService` the local API uses, so
single-flight, runtime safety policy, and state validation apply identically.

### 7.2 Deduplication

Delivery is at-least-once; execution is at-most-once.

* `command_id` is the deduplication key.
* The Node stores the command **before** acknowledging acceptance.
* A redelivered `command_id` with the **same** payload digest returns the stored
  outcome with `"deduplicated": true`; the work is not repeated.
* A redelivered `command_id` with a **different** payload digest is
  `duplicate_payload_mismatch` — a protocol violation.
* Payload digests are SHA-256 over `{command, project_id, payload}`.
* A daemon restart never re-executes a settled command. Commands caught mid
  execution are surfaced for reconciliation and are **not** replayed
  automatically, because a partially executed command may already have had an
  effect.

### 7.3 Projects

`project_id` must name a project registered on the Node. The Control Plane never
supplies, overrides, or learns a host filesystem path: `projects.list` returns
identity and state only. An unregistered or disabled id yields
`project_not_registered`.

## 8. Events

Subscription is a command:

```json
{"command": "events.subscribe", "project_id": "phase-a",
 "payload": {"run_id": "arun_...", "from_seq": 0}}
```

Delivery, Node → Control Plane:

```json
{
  "type": "client.event",
  "payload": {
    "project_id": "phase-a",
    "run_id": "arun_...",
    "seq": 7,
    "event_type": "tool.started",
    "recorded_at": 1786475448672,
    "payload": {}
  }
}
```

Acknowledgement, Control Plane → Node:

```json
{"type": "server.event.ack", "payload": {"run_id": "arun_...", "acked_seq": 7}}
```

Rules:

* the durable **event journal** is the source of truth; events are never copied
  into a second durable store;
* only the subscription cursor is persisted, so state is reconstructible after
  reconnect;
* delivery is strictly **after** `acked_seq`;
* `acked_seq` is the highest **contiguous** sequence the Control Plane has
  durably stored, and it never moves backwards;
* ordering is guaranteed **per run**;
* duplicate delivery is permitted and harmless — the receiver keys on `seq`;
* a terminal run can be replayed in full without contacting the execution
  backend;
* a slow Control Plane cannot block run execution: the pump reads the journal at
  its own pace and the worker never waits on it;
* unknown or unauthorized run ids are rejected;
* payloads are redacted before transmission.

## 9. Outbox

Messages that cannot be re-derived from the event journal — command results,
terminal outcomes, drain acknowledgements — are persisted **before** being sent
and are retained until acknowledged. After a reconnect they are resent in
insertion order. Duplicate receipt is harmless.

When the outbox reaches its bound (1024 unacknowledged entries), the Node
**refuses new remote commands** rather than accepting work whose result it could
not report. Heartbeats are not persisted.

## 10. Error codes

| Code | Meaning |
| --- | --- |
| `malformed_frame` | Unparsable or structurally invalid frame |
| `frame_too_large` | Exceeds 1 MiB |
| `unsupported_version` | No shared protocol version |
| `unknown_message_type` | Type not understood |
| `not_authenticated` | Message sent before `server.ready` |
| `authentication_failed` | Signature did not verify |
| `challenge_expired` | Challenge used after `expires_at` |
| `challenge_replayed` | Server nonce reused |
| `unknown_node` | `node_id` has no registered key |
| `payload_too_large` | Command payload exceeds 128 KiB |
| `unknown_command` | Allowed but not implemented |
| `forbidden_command` | Outside the allow list |
| `project_not_registered` | Unknown or disabled project |
| `duplicate_payload_mismatch` | Command id reused with different work |
| `command_failed` | Execution failed; detail in the result |
| `internal` | Node-side failure |

## 11. State machines

**Connection**

```
disabled ─── no URL configured
unenrolled ─ URL configured, no node_id
connecting → authenticating → connected
     ▲                            │
     └──── backing_off ◀──────────┘   (exponential, bounded, jittered)
connected → draining               (remote node.drain, or shutdown)
failed  ─── configuration error retrying cannot fix
```

Backoff doubles from `initial_backoff_ms`, is capped at `max_backoff_ms`, and
jitter only ever **shortens** a delay so the ceiling always holds. A session that
stays up for `stable_session_ms` resets the sequence.

**Remote command**

```
received → accepted → executing → completed | failed
received → rejected
```

`completed`, `rejected`, and `failed` are terminal; a terminal command is never
re-executed.

## 12. Security considerations

* TLS authenticates the server; Ed25519 challenge-response authenticates the
  Node. Neither substitutes for the other.
* Replay protection is nonce-based. `timestamp` is informational and must never
  be used for it.
* The domain separator binds every signature to this protocol and version.
* The private key never appears in an argument, an environment variable, a log,
  the local API, or a container mount.
* The enrollment token is used once and never stored.
* The Control Plane can address only registered project ids and can never supply
  a host path.
* The command allow list is closed: there is no escape hatch to shell, Docker,
  credentials, or identity export.
* `node.drain` stops new work. It cannot stop the daemon, stop Docker, remove a
  project, or affect the host.
* All persisted and transmitted payloads are recursively redacted.
* A Control Plane that is offline, unauthenticated, slow, or hostile degrades
  nothing locally: the Unix-socket API and run execution continue.

## 13. Conformance fixtures

`docs/protocol/fixtures/v1/` holds language-neutral inputs and the outputs each
implementation derives from them:

| File | Written by | Validated by |
| --- | --- | --- |
| `inputs.json` | hand-authored | both |
| `outputs.rust.json` | Rust Node | TypeScript Control Plane |
| `outputs.typescript.json` | TypeScript Control Plane | Rust Node |

Each implementation recomputes every derived value from `inputs.json` and
asserts the *other* language's committed outputs match. Covered: the public key
and fingerprint, the canonical transcript bytes, the signature, one variant per
signed field, digest vectors including key ordering and Unicode, command
fingerprints, the allowed command set, invalid frames with their error codes,
forward-compatible frames, and replay cursor rules.

The Ed25519 key in the fixtures is a dedicated test key with a published seed.
It has never protected anything and must never be used elsewhere.

## 14. Not in v1

Node identity rotation, multi-Control-Plane failover, server-initiated identity
revocation, compression, and binary framing. Adding any of them requires a new
protocol version negotiated through §4.
